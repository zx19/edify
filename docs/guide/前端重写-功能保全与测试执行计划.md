# 前端重写：功能保全与测试执行计划

> 重写派路线的执行附件，配套 `web/docs/rewrite-plan.md`。  
> 核心机制：**双轨对照**——旧版（Dify 原前端）与新写版并行运行，同一套功能矩阵 / 测试 / e2e 各跑一遍，diff = 0 才算一项追平。重写不是"写完新的删旧的"，而是"新的一项一项追平旧的，每追平一项旧的可删"。
>
> 已确认前提（2026-09-09）：① 重写前端 = 合法解除 LICENSE 1b（不买许可）；② RBAC 本地化不做，`RBAC_ENABLED` 维持 false，前端「角色与权限」「权限集」tab 一期降级/不迁移；③ 多空间非多租户，1a 不触发。
>
> 实测基线（2026-09-09）：路由 140 个 page/layout（commonLayout 21 子目录 + shareLayout 5 类型 + 认证 8）；web/models 11 个契约文件；spec 97 个；dify-ui 47 目录(~40 原语)；i18n 24 语言/每语言 18 文件 78 处 Dify 字样；e2e 37 feature。

> ⚠️ **可行性部分验证（2026-09-09 架构嗅探）**：  
> **已验证**：① 构建链 = Vite + vinext 插件（vinext 是让 Vite 跑 Next.js App Router 的兼容层，外部 npm 包非自研）；② dify-ui 与 web 耦合 = **纯原语 import 无 context/provider 渗透**（dify-ui exports 白名单只原语+cn+styles.css，web 全走原语路径），逐原语替换可行；③ 包名替换连锁但机械可做（web 依赖 5 个内部 workspace 包）。  
> **待修正**：包名替换是批量改包名 + pnpm install 重生成 lock（**非 tsconfig path alias**，方案原描述错）；契约层是 **oRPC**（`@orpc/contract`）非 models 文件，契约冻结要从 oRPC contract 提取；状态层 jotai+zustand+react-query 多套并存。  
> **vp 双轨机制已验证可行（2026-09-10）**：`vp run` 是 workspace task runner（`vp run <pkg>#<task>` 按包名选 task，`--filter`/`--parallel` 支持多包），加 web-new workspace 包即可 `vp run dify-web-new#dev:vinext` 双跑——机制层支点解除。**实做 PoC 可选**：cp web→web-new + 改 port + 加 workspace + install + 跑 dev，确认 vinext 独立起 dev 无坑（会动 pnpm-lock，PoC 后还原）。

## 0. 核心机制：双轨对照（三锚点的统一实现）

```
旧版 web (Dify 原前端, :3000)          新写版 web (杏树林, :3001)
        │                                       │
        ├── 同一套功能矩阵 M ──────────────────┤  (功能不丢失)
        ├── 同一套测试 2114 ────────────────────┤  (不退步: 数量/coverage 不降)
        ├── 同一套 e2e 37 feature ──────────────┤  (不退步: 行为一致)
        └── 同一套视觉基线 ─────────────────────┘  (视觉回归: diff 在阈值)
```

**铁律**：新写版任何一项功能，必须在这四条上对齐旧版才算"追平"，追平后旧版对应代码才可删。**禁止"先删旧再写新"**——那等于自断对照。

## 第 0 步：固化三份基线（重写前必做，2~3 周）

> 没有基线就无法对照。这一步产出三份"标尺"，贯穿全程不变。

### 0.1 功能矩阵基线（锚点①：防丢失）

**做什么**：穷举旧版全部功能点，组成矩阵 M，每行一个功能，列 = {路由, 契约字段, i18n key, 测试, e2e step}。

**具体动作**：

| 子步      | 工具/命令                                                                                            | 产出                               |
| ------- | ------------------------------------------------------------------------------------------------ | -------------------------------- |
| 路由穷举    | `find web/app -name "page.tsx" -o -name "layout.tsx"` → 140 项，按 commonLayout/shareLayout/auth 分组 | `baselines/routes.json`          |
| 契约固化    | 提取 `web/models/*.ts`（11 文件）所有 type/interface 字段 + `web/service/*/` 所有 fetch 调用的 URL+method       | `baselines/contracts.json`       |
| i18n 穷举 | en-US 为基准（6484 key），每 key 记录 {文件, key, 值, 引用组件}                                                  | `baselines/i18n-keys.json`       |
| 测试功能点   | 扫 97 spec + dify-ui spec，提取每个 describe/it 标题 → 功能点                                               | `baselines/test-points.json`     |
| e2e 旅程  | 37 feature 的 Given/When/Then 逐条提取 → 用户旅程清单                                                       | `baselines/e2e-journeys.json`    |
| 合并      | 脚本 `scripts/build-function-matrix.mjs`（仿现有 `de-dify-inventory.mjs`）把上述五份按"功能"归并                  | `baselines/function-matrix.json` |

**验收**：`function-matrix.json` 每行五列非空率 ≥ 90%（少数功能可能没 e2e 或没测试，允许空但要登记为"测试缺口"单独跟踪）。

### 0.2 测试基线（锚点②：防退步）

**做什么**：固化现状测试的数量、通过率、coverage，作为迁移后"不降"的标尺。

**具体动作**：

| 子步           | 命令                                                              | 产出                             |
| ------------ | --------------------------------------------------------------- | ------------------------------ |
| 单元测试基线       | `pnpm test --coverage` → 记录测试数（~2114）、通过率（须 100%）、各目录 coverage% | `baselines/test-snapshot.json` |
| e2e 基线       | `pnpm test:e2e` → 37 feature 全绿，录 trace + 视频                    | `baselines/e2e-baseline/`      |
| dify-ui 契约冻结 | 导出 `packages/dify-ui` 全部 public API 签名（props/方法）                | `baselines/dify-ui-api.json`   |

**验收**：测试 100% 绿、e2e 100% 绿、dify-ui API 冻结文件入库 git（后续任何 public API 变更需显式登记）。

### 0.3 视觉基线（锚点③：防偏差）

**做什么**：旧版全量截图，作为新版视觉回归对照。

**具体动作**：

| 子步   | 工具                                                                    | 产出                       |
| ---- | --------------------------------------------------------------------- | ------------------------ |
| 全量截图 | Playwright `screenshot({ fullPage: true })` 遍历 140 路由 + e2e 37 旅程的关键步 | `baselines/screenshots/` |
| 配置   | `playwright.config.ts` 加 `toHaveScreenshot` 基线目录指向上述                  | 视觉回归可用                   |

**验收**：140 路由截图齐全，目录大小可控（可按断点分 desktop/mobile 两套）。

## 第 1 步：搭双轨脚手架（1 周）

**做什么**：让旧版 :3000 / 新写版 :3001 可同时启动、共用同一套测试与 e2e 配置。

**具体动作**：

| 子步      | 动作                                                                                                          | 产出                                  |
| ------- | ----------------------------------------------------------------------------------------------------------- | ----------------------------------- |
| 双端口启动   | `package.json` 加 `dev:legacy`(:3000) / `dev:new`(:3001)，共用 vinext 配置                                        | 双轨可起                                |
| e2e 双轨  | `playwright.config.ts` 加 `projects: [legacy, new]`，同 feature 文件跑两遍，baseURL 各自指向                             | `e2e:diff` 脚本输出两版行为 diff            |
| 测试双轨    | Vitest 配置不变（新写版从零写测试，旧版测试不动；迁移时"搬"测试不"重写"）                                                                  | —                                   |
| 功能矩阵对照器 | 脚本 `scripts/matrix-check.mjs`：读 `function-matrix.json`，对新写版逐行验证落点（路由存在/契约字段匹配/i18n key 存在/测试存在/e2e step 可跑） | `reports/matrix-coverage.md`（追平率 %） |

**验收**：`pnpm e2e:diff` 能输出新旧两版 e2e 行为 diff 报告；`matrix-check` 能输出追平率。

## 第 1.5 步：token 共享层（0.5~1 周，三线共用）

**做什么**：把 design §3.2 定稿的视觉变量值（白+黑+橙 + light/dark + accent 覆盖 chat_color_theme）落地为**共享 CSS 变量文件**，三线各自作用域类引用同一套变量值：

- `.admin-theme`（系统管理控制台）
- `.webapp-theme`（WebApp，含 chat_color_theme 注入 accent 覆盖）
- `.console-theme`（工作台控制台）

**为什么独立前置**：token 是所有新原语 + 三条线主题的视觉底座。抽出来让系统管理控制台全新框架不卡在 3a（WebApp 应用地基）、WebApp 不卡在控制台——三条线各消费 token 共享层，不互相等。系统管理控制台只需 token 共享层（本步）+ 2a 原语 + admin 端点即可启动全新框架，**不依赖 3a**。

**验收**：三作用域类挂载 + design 变量值落地 + 三线各引同一 CSS 文件 + dark 变体定义。

## 第 2 步：逐原语迁移 dify-ui（3~4 周，M1）

**做什么**：dify-ui 47 目录(~40 原语)逐个重写，换到杏树林命名空间。这是牵动面最大的一步（web 1720 文件 import 它），必须原子化。

**每原语一个闭环（以 button 为例）**：

| 子步     | 动作                                                              | 验收                        |
| ------ | --------------------------------------------------------------- | ------------------------- |
| 1 冻结契约 | 读 `baselines/dify-ui-api.json` 的 button props                   | API 签名固定                  |
| 2 重写   | 新包名下实现 button，props 100% 对齐冻结签名                                 | 新 button 单测绿              |
| 3 双轨替换 | tsconfig path alias 把 `@langgenius/dify-ui/button` 指向新版（旧版代码保留） | 旧测试不改动仍绿                  |
| 4 全量验证 | `pnpm test && pnpm test:e2e && ppm screenshot:diff`             | 2114 不降、e2e 绿、视觉 diff = 0 |
| 5 删旧   | 确认 4 通过 → 删旧 button 实现                                          | 编译绿                       |

**关键**：每原语走完 1~~5 才动下一个。**不允许批量改 40 个再测**——失败时无法定位。预计 40 原语 × 0.5~~1 天 = 3~4 周。

**拆 2a/2b（WebApp 优先，2026-09-09 用户决策）**：原语按消费方分两批迁，WebApp 子集先行：

- **2a WebApp 原语子集**（~~15~~20 个，1.5~2 周）：WebApp 实际 import 的原语（share/text-generation 实测含 button/cn/select/textarea/dialog/icon-button/toast/dropdown-menu/tabs，全 share+shareLayout 待第 0 步精确扫描）。迁完 2a 即具备 WebApp 重写条件，不必等控制台原语。
- **2b 控制台原语子集**（剩余 ~~20 个，1.5~~2 周，后做）：控制台独有 + 两边共用里 2a 未覆盖的。

**衔接点①（login/setup）**：迁移到 signin/dialog 原语时，同步迁权限方案 §6.1.1 的 `is_system_admin` 放行分支（后端流 B 先在 Dify 前端落地，重写时迁入新前端）。这一步要后端流 B 的 login 改造先就位。**注意：2a 不触发衔接点①**（WebApp 免登录、不走 signin），衔接点①在 **3b 控制台地基的 signin 迁移**时触发（2b 只迁原语、不碰 login 逻辑）。

## 第 4 步：WebApp 主旅程（提前，3~4 周，M3a）

**做什么**：webapp 五类型重写（含底层共用件一并重写，见下方规格引用）。这是 WebApp 提前后的首个对外可见成果。

**迁移顺序**（按功能矩阵覆盖率从高到低）：

1. chat（type 1，含 Agent App——`/agent` 死路由合并 `/chat`，功能清单最全作范本）
2. chatbot（type 2，embedded，iframe 通信须保留）
3. completion（type 3）
4. workflow（type 4）+ env-workflow（type 5）

**每模块验收**：功能矩阵该类型所有行追平（5 列全绿）+ e2e 该类型 feature 双轨 diff = 0 + 视觉回归通过 + design 三件套功能对照表逐项核销。

### 第 4 步业务组件设计时机（混合模式：全局 token 提前 + 单元级三件套交织）

> 业务组件重新设计**不统一提前做所有 mockup**（3700 组件/几十单元不现实），也**不边写代码边临时设计**（一致性失控）。design §4.1 本就「mockup 逐类型先行」——混合模式：

| 层               | 时机                          | 内容                                                                     |
| --------------- | --------------------------- | ---------------------------------------------------------------------- |
| **全局 token 层**  | 提前（第 0 步确认定稿 + 3a 落地共享 CSS） | design §3.2 已定稿（白+黑+橙 + `.webapp-theme` 作用域 + light/dark）。所有业务组件共用，不各做 |
| **共享壳层 mockup** | 第 4 步首个单元（chat）时做范本         | `chat-with-history`/`text-generation` 壳层骨架（多类型共用），首单元范本，后续复用           |
| **各单元 mockup**  | **到该单元迁移时做**（与代码交织）         | 单元启动先做三件套（QA 实证清单 → mockup → 功能对照表），再重写代码                              |

**单元内设计-代码交织流程**（每业务组件单元）：  
QA 实证清单（旧版功能）→ mockup（新设计，对照 token）→ 功能对照表（逐项映射）→ 重写代码 → 3.2 四项验收。设计假设在重写时立即验证，不成立马上改 mockup（不返工到全局）。

**跨单元一致性保证**：前置 token 层（全局底座）+ 每单元 mockup 评审（对照 token 规范）+ 共享壳层（骨架共用）。**不靠"一次性设计所有 mockup"保证**。

**为什么不统一提前**：① 几十单元一次设计完周期太长，延后见成果；② 设计-实现脱节（mockup 假设到实现才发现不成立要返工）。**为什么不边写边临时设计**：① 一致性失控（各单元各设计）；② 缺功能对照表核销会丢功能。混合模式兼顾一致性与灵活性。

## 第 6 步：次级模块 + 删减（4~6 周，M4）

**做什么**：知识库/工具/账户/skills + 删除不需要模块（education、部分 marketplace、多余语言包）。

## 组件级执行细则（单个组件怎么重写——前面讲"顺序"，这里讲"动手"）

> `web/app/components` 下约 3700 个 `.tsx`，**不逐个迁**——按"功能单元"聚类（一个壳层 + 其子组件群 = 一个迁移单元，对应第 0 步功能矩阵的一个模块行）。每个迁移单元内部，每个组件遵循同一套"契约冻结 → 重写 → 双轨渲染 → 三层 diff → 删旧"闭环。

### 1. 迁移单元与依赖拓扑（先建，定顺序）

| 子步   | 动作                                 | 工具/命令                                                                               | 产出                                              |
| ---- | ---------------------------------- | ----------------------------------------------------------------------------------- | ----------------------------------------------- |
| 组件清单 | 扫 `web/app/components/**/*.tsx` 全量 | `find` 或 Glob                                                                       | `baselines/components.json`（路径 × props 接口名）     |
| 依赖图  | 按 `import` 关系建图，拓扑排序               | `madge --extensions tsx,ts --ts-config web/tsconfig.json web/app/components --tree` | `baselines/component-graph.json`（叶子→中层→顶层顺序）    |
| 聚类   | 按路由/模块把组件归为 ~几十个迁移单元               | 脚本 + 功能矩阵模块分组                                                                       | `baselines/migration-units.json`（单元 × 含组件 × 入度） |

**迁移铁律**：**叶子组件先迁**（无 Dify 内部依赖，如纯展示件）→ 中层组合 → 顶层页面。每迁完一组件，更新图标记，依赖它的组件解锁。**禁止迁组合件时叶子还没迁**——会临时回退旧版叶子，破坏对照。

### 2. 单组件重写闭环（每个组件五步，与原语同构但契约源不同）

| 步         | 动作                     | dify-ui 原语（第 2 步）                                                   | 业务组件（第 4/5 步）                                                                 |
| --------- | ---------------------- | ------------------------------------------------------------------- | ----------------------------------------------------------------------------- |
| 1 冻结契约    | 提取 props 签名            | 源 = `packages/dify-ui` 已冻结 public API（`baselines/dify-ui-api.json`） | 源 = 从 Dify 现有组件 `.tsx` 的 `interface`/`type` 提取 → `contracts/<component>.json` |
| 2 重写      | 新命名空间下实现，props 100% 对齐 | 新包名下                                                                | `web/app` 新代码                                                                 |
| 3 双轨渲染    | 同一组 props 旧/新版各渲染一遍    | tsconfig path alias 切换                                              | 同 props 两个 import 各跑                                                          |
| 4 三层 diff | DOM / 行为 / 视觉对齐        | 见下表                                                                 | 见下表                                                                           |
| 5 删旧      | 4 全绿 → 删旧实现            | 删 packages/dify-ui 旧                                                | 删 web/app 旧                                                                   |

### 3. 组件级追平机制（按组件类型分两套——核心修正）

> ⚠️ **关键区分（2026-09-09 用户洞察）**：业务组件视觉不变地重写 = 代码级换皮，无意义。重写派独特价值在 **license(1b) + 代码主权 + 命名空间去 Dify 化**，不在视觉差异化（视觉差异化换皮派也能做）。两类追平机制不同：
>
> - **基础组件**（dify-ui 原语 + 纯展示叶子）：视觉对齐 Dify 原 → **三层 diff**（视觉接近 0，下表）
> - **业务组件**（壳层 + 复合，如 chat-with-history）：**重新设计**（按 design 新语言，V1 就落地）→ **功能对照表 + 行为对齐**（3.2），视觉必然变，不走视觉 diff
>
> **design 三件套（QA 实证清单 → mockup → 功能对照表）= 业务组件的追平机制**，替代视觉 diff。

**基础组件的三层 diff**（业务组件见 3.2，不走此表）：

| 层      | 方法                                   | 工具                                                                                                        | 验收                |
| ------ | ------------------------------------ | --------------------------------------------------------------------------------------------------------- | ----------------- |
| DOM 结构 | 同 props 渲染两版，DOM 快照 diff             | Vitest + `@testing-library/react`，同一 test 文件 import 旧/新各跑一遍                                               | diff = 0          |
| 行为     | 同交互（click/input/submit），两版回调/状态 diff | Vitest，同 test cases 跑两版                                                                                   | diff = 0          |
| 视觉     | 同 props 截图两版，像素 diff                 | Storybook 双 stories（`<Component>.legacy.stories.tsx` + `.new.stories.tsx`）+ Playwright `toHaveScreenshot` | 像素 diff 在阈值（0.1%） |

**props 矩阵**：契约冻结后，对每个组件生成一组"代表性 props 组合"（含边界值：空列表/加载态/错误态/最大长度），三层 diff 在所有组合上都过才算追平。


### 3.1 基础组件对齐判定（三层 diff，视觉对齐 Dify 原）

> 适用范围：仅基础组件（dify-ui 原语 + 纯展示叶子）。业务组件重新设计，见 3.2。  
> 核心约束（仅基础组件）：视觉对齐 Dify 原——换命名空间/解除 1b/断流，视觉不变是手段。视觉接近 0 是基础组件去 Dify 化的硬验收。

**0 层 契约对齐（前置，类型层）**

- 比较对象：新版组件 props 接口 vs `contracts/<component>.json` 冻结签名
- 判定：字段名 / 类型 / 必填 / 默认值 100% 匹配 → `tsc --noEmit` 编译通过 = 过；任一字段缺失/类型漂移 = 不过
- 工具输出：tsc 错误数 = 0

**1 层 DOM 结构对齐**

- 比较对象：同 props 渲染两版，取 `prettyDOM()` 序列化字符串做 diff
- normalize（去噪声，diff 前必做）：
  - 剥离动态值——React key、随机 `id`/`aria-*`、内联 `style` 动画值（transform/opacity 过渡中）、时间戳
  - 保留语义结构——标签层级、文本内容、`data-testid`、`role`
- 去 Dify 化白名单（预期差异，登记到 `baselines/allowlist.json`）：
  - class 名映射（`dify-button` → `xsl-button`）
  - 组件命名空间 import 路径（`@langgenius/dify-ui` → `@xsl/ui`）
  - 包名（`dify-web` → `xsl-web`）
- 判定：normalize + 白名单过滤后，**非白名单 diff 行数 = 0** = 过；任一非白名单结构差异（多了/少了标签、文本变了、语义 attr 变了）= 不过
- 工具：`@testing-library/react` `prettyDOM` + 自写 normalize + `jest-diff`

**2 层 行为对齐**

- 比较对象：同 props + 同交互序列，两版的"行为快照" = {回调调用序列 + 每次参数 + 最终 state + 触发的 fetch 请求体/响应处理}
- 控制噪声（消除时序差异）：`vi.useFakeTimers()` + msw（mock service worker）拦截 fetch 给同响应
- 判定：行为快照**完全相等**（回调序列 / 参数 / state / 请求 四者全等）= 过；任一处不一致 = 不过——**行为是布尔判定，无阈值，不容差**
- 工具：Vitest `vi.fn()` 记录调用 + msw 拦截 + 自写行为快照序列化

**3 层 视觉对齐**

- 比较对象：同 props 截图两版，Playwright `toHaveScreenshot` 内置像素 diff
- 控制噪声：等稳定态截图（`locator.waitFor({ state: 'visible' })` + 等动画/过渡结束）；可配 `prefers-reduced-motion` 禁动画截图
- 判定：`maxDiffPixelRatio: 0.001`（0.1%，抗锯齿/子像素渲染的容忍上限）—— **diff < 0.1% = 过**；超阈值必须人工判定：
  - "故意改视觉"（V2 升级）→ 登记到 `reports/visual-changes.md` + 更新基线
  - "退步"（ unintended ）→ 必修，不算追平
- 特殊：重写追平期视觉 diff 应**接近 0**——因为 V1 要求视觉不变（只改代码不改视觉），视觉层接近 0 本身就是去 Dify 化的硬验收（证明去 Dify 化没破坏视觉）

**白名单审计（防借白名单掩盖退步）**：

- 白名单 `baselines/allowlist.json` 的每条变更需 git commit message 说明 + 关联迁移单元
- CI 守卫：白名单条目数只增不减（除非删对应旧代码），异常增长告警
- 定期抽查：随机抽白名单条目，人工核验确属"去 Dify 化预期差异"而非"真退步被白名单豁免"

### 3.2 业务组件对齐判定（功能对照表 + 行为对齐，视觉重新设计）

业务组件重写 = **重新设计**（视觉/布局/交互形态按 design 白+黑+橙），V1 业务组件层就落地新视觉。**不走三层视觉 diff**（视觉必然变）。追平机制：

| 层  | 方法                                                           | 判定                               |
| -- | ------------------------------------------------------------ | -------------------------------- |
| 功能 | design 三件套第三件——功能对照表：现状功能 → 新设计落点逐项映射                        | **每行有落点 = 过**（无落点 = 设计不通过，该类型重做） |
| 行为 | 同交互两版行为快照对齐（同基础组件第 2 层：fake timers + msw，回调序列+参数+state+请求全等） | 完全相等 = 过                         |
| 契约 | props 对齐（同基础组件第 0 层）                                         | tsc 编译过 = 过                      |
| 视觉 | **不对齐旧版**（必然变）——对**新设计自身**建基线：mockup 评审通过 + 新基线视觉回归绿         | mockup 过 + 新基线回归绿 = 过            |

**关键**：业务组件追平 = **功能不丢（对照表）+ 行为不变（行为对齐）+ 视觉升级（design）**，不是视觉 diff=0。视觉验收是对新 mockup 自身建基线（Playwright 对新设计截图），而非对旧版。

**业务组件重写的意义**：借重写重新设计交互/视觉（design 驱动）+ 解除 1b（新代码不复制 Dify 业务组件）+ 断流自主。视觉差异化是 design 驱动、与换皮/重写正交——重写的独特价值仍是 license + 代码主权。

### 4. 组件级验收清单（按类型分两套）

**基础组件**（四项，视觉对齐 Dify 原）：

- [ ] 契约对齐（props 100% 匹配 `contracts/<component>.json`）
- [ ] DOM / 行为双轨 diff = 0（props 矩阵全过）
- [ ] 视觉双轨通过（像素 diff < 0.1%）

四项全绿 → 追平，删旧，解锁依赖者。

**业务组件**（四项，视觉重新设计）：

- [ ] 行为对齐（行为快照全等，同基础组件第 2 层）
- [ ] 功能对照表逐项核销（每功能有落点，design 三件套第三件）
- [ ] mockup 评审通过 + 新基线视觉回归绿

四项全绿 → 追平，删旧，解锁依赖者。

一个迁移单元（如 `chat-with-history` 壳层 + 其子组件群）追平 = 单元内**所有组件**按类型四项全绿（基础走 3.1、业务走 3.2）+ 该单元路由的 e2e feature 双轨 diff = 0 + 功能矩阵该模块行 5 列全绿。单元追平后，旧版整个单元目录可删。
