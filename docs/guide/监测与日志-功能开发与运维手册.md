# 监测与日志机制说明：功能、开发与运维手册

> 面向本仓库（edify / lomva 部署）的研发与运维。
> 内容来源：Dify 官方文档（monitor 系列）与本仓库实际代码/部署配置。
> 官方入口：<https://docs.dify.ai/zh/self-host/use-dify/monitor/analysis>

## 1. 概述

应用监测由四块组成：

| 板块 | 回答的问题 | 数据落点 |
|---|---|---|
| 数据分析 Dashboard | 用量趋势如何（消息/用户/token/满意度） | 实时扫 `messages` / `conversations` / `workflow_runs` 表 |
| 日志与标注 | 每次对话/运行发生了什么 | `conversations` / `messages` / `workflow_app_logs` / `workflow_node_executions` 等 |
| 第三方 Tracing | 深入性能分析（Langfuse/LangSmith/腾讯 CLS…） | 事件 → 对象存储 → Celery 异步分发到外部平台 |
| OTel 基础设施（可选） | Dify 服务自身的可观测 | api/worker 进程 → OTLP endpoint |

## 2. 功能总览（官方使用侧）

### 2.1 数据分析 Dashboard（应用详情 → 概览）

- 指标：**Total Messages**（对话量）、**Active Users**（产生过一次以上互动的用户）、**Average User Interactions**（每会话互动深度）、**Token Usage**（资源消耗与成本）；另有满意度、平均响应、Token/s 等（随应用类型不同而不同，见 §3.1）。
- 顶部时间选择器切换统计区间。
- 入口「Tracing app performance」可接外部观测平台。
- 统计均**排除调试来源**（调试预览不计入）。

### 2.2 日志（应用详情 → 日志）

- 每行 = 一次会话或一次运行：标题（取自首条消息）、终端用户/成员、用户/团队评分；Workflow 应用额外显示触发方式（WebApp / Webhook / Schedule / Integration）。
- 详情：完整消息线程、token 消耗与延迟、原始 prompt、Agent 工具迭代、Chatflow/Workflow 的逐节点 trace；Workflow 支持「Test With Params」带参重跑；可加团队评分与标注。
- 保留期：**默认永久保留**；自动清理为每日定时任务（配置见 §5.1）。
- 无导出功能（标注与反馈除外），可复制浏览器地址分享单条日志。

### 2.3 标注回复（Annotation Reply）

- 用途：建立「标准答案库」——用户提问先做语义匹配，命中则直接返回预设答案，不再调模型。
- 启用：编排页 → Add Features → 标注回复，配置 **相似度阈值** 与 **embedding 模型**（换模型会重建全部标注向量）。
- 录入：调试/日志中把 AI 回答编辑存为标注；标注页手动录入；CSV 模板批量导入；支持导出与命中历史查看。

### 2.4 第三方 Tracing

- 应用详情 → 概览 →「Tracing app performance」配置（以 Langfuse 为例：填 Host / Public Key / Secret Key，显示 started 即生效）。
- 上报内容：Workflow/Chatflow 执行（含逐节点）、消息与 LLM 调用（token、模型、状态）、内容审核、建议问题、知识库检索、工具调用、会话命名等。
- 支持平台：Langfuse、LangSmith、Opik、Weave、Arize/Phoenix、阿里云 ARMS、**腾讯云 CLS**、MLflow/Databricks。

## 3. api 后端代码地图

### 3.1 统计接口（实时扫表，无聚合无缓存）

普通应用 `controllers/console/app/statistic.py`，前缀 `/console/api/apps/<app_id>/statistics/`：

| 端点 | 口径（全部 `invoke_from != DEBUGGER`） |
|---|---|
| `daily-messages` | `messages` 按天 COUNT |
| `daily-conversations` | COUNT(DISTINCT conversation_id) |
| `daily-end-users` | COUNT(DISTINCT from_end_user_id) |
| `token-costs` | SUM(message_tokens+answer_tokens)、SUM(total_price) |
| `average-session-interactions` | conversations JOIN messages，平均每会话消息数 |
| `user-satisfaction-rate` | like 数 / 总消息（JOIN message_feedbacks） |
| `average-response-time` | AVG(provider_response_latency) |
| `tokens-per-second` | SUM(answer_tokens)/SUM(latency) |

Workflow 应用 `controllers/console/app/workflow_statistic.py`（4 个端点，前缀 `.../workflow/statistics/`），经 repository `repositories/sqlalchemy_api_workflow_run_repository.py` 扫 `workflow_runs`（仅 `triggered_from=APP_RUN`）。

**维护要点**：统计 SQL 直接写在控制器里、**实时扫原始表、无聚合表无缓存**——消息量大的应用打开概览页就是一次范围扫描；日期按用户时区转换（`libs.helper.convert_datetime_to_date`）。权限点 `RBACPermission.APP_MONITOR`。**没有并发会话统计端点**（只有 `App.max_active_requests` 限流配置）。

### 3.2 日志

- 会话/消息日志：`controllers/console/app/conversation.py`（chat/completion 会话列表与详情）、`message.py`（消息列表/详情/反馈导出）。
- Workflow 日志：`controllers/console/app/workflow_app_log.py`（`GET /apps/<id>/workflow-app-logs`、`workflow-archived-logs`）→ `services/workflow_app_service.py`；表：`workflow_runs`、`workflow_node_executions`（`core/app/workflow/layers/persistence.py` 写入）、`workflow_app_logs`（仅非调试来源）、归档表 `workflow_archive_logs`。
- 归档/清理：`tasks/workflow_run_archive_download_tasks.py`、`schedule/clean_workflow_runs_task.py`、`clean_workflow_runlogs_precise.py`。

### 3.3 标注回复

- 控制器 `controllers/console/app/annotation.py`：CRUD、启停（`annotation-reply/<enable|disable>`）、阈值设置、批量导入（CSV）/导出、命中历史。
- 服务 `services/annotation_service.py`；模型：`MessageAnnotation`、`AppAnnotationSetting`（阈值/embedding）、`AppAnnotationHitHistory`（命中计数）。

### 3.4 第三方 Tracing 架构

```
① 运行时回调 → TraceQueueManager 进程内内存队列（ops_trace_manager.py:1506）
② 定时器批量收集 → 事件序列化写 storage（ops_trace/{app_id}/{uuid}.json，:1542-1565）
   → process_trace_tasks.delay() 投递 Celery 队列「ops_trace」
③ worker 消费：读回 JSON → 重建实体 → 解密应用配置实例化 provider → trace_instance.trace()
④ provider 包经 HTTPS 上报外部平台；失败按 Celery 重试（60 次 × 5s），终态失败删缓冲文件
```

设计含义：**先落文件再发 Celery** 是因为 trace payload 大、走 broker 会撑爆 Redis；代价是 **api 与 worker 必须共享同一份 storage**（当前 QA 的 CFS RWX 满足；若 api 改本地独占卷，trace 会静默失败）。provider 包**不经 SSRF 代理、直连配置的 Host**——公网 SaaS 需 api/worker 出公网，内网部署建议腾讯 CLS 或自建 Langfuse 填内网地址。

- 调度核心 `core/ops/ops_trace_manager.py`：配置存 `trace_app_config` 表（按 app_id+provider，敏感字段按 tenant 加密），开关存 `App.tracing` JSON；读取解密+脱敏。
- 配置接口：`GET/POST /apps/<id>/trace`（开关+provider，`console/app/app.py:1207/1229`）、`GET/POST/PATCH/DELETE /apps/<id>/trace-config`（凭证，`console/app/ops_trace.py`）。
- **provider 实现已插件化为独立包**：`api/providers/trace/trace-langfuse/`、`trace-langsmith/`、`trace-tencent/`（CLS）等；事件类型枚举 `core/ops/entities/trace_entity.py:279`（WORKFLOW/MESSAGE/NODE/MODERATION/SUGGESTED_QUESTION/DATASET_RETRIEVAL/TOOL/GENERATE_NAME 等 TRACE）。
- 重试：`OPS_TRACE_RETRYABLE_DISPATCH_MAX_RETRIES=60`、间隔 5s（`configs/feature/__init__.py:1327`）。

### 3.5 OTel（Dify 自身可观测，独立于上）

`ENABLE_OTEL` + `OTLP_BASE_ENDPOINT` 等（`configs/observability/otel/`）；instrument Flask/Celery/SQLAlchemy/Redis/HTTPX（`extensions/otel/instrumentation.py:152`）；workflow 节点级 span（`core/app/workflow/layers/observability.py`）；`X-Trace-Id` 透传（`core/helper/trace_id_helper.py`）。

## 5. 部署与运维（本仓库）

### 5.1 日志保留（**当前默认不清理，注意**）

docker 模板（`docker/envs/core-services/shared.env.example:100-103,260`）：

```
WORKFLOW_LOG_CLEANUP_ENABLED=false      # 默认关；开=true 后每日清理
WORKFLOW_LOG_RETENTION_DAYS=30
WORKFLOW_LOG_CLEANUP_BATCH_SIZE=100
ENABLE_CLEAN_MESSAGES=false             # 会话消息清理，同样默认关
```

**k8s overlay 均未覆盖这两项 → QA/prod 日志永久保留，`messages` / `workflow_runs` 等表会无限增长**（同时还拉慢 §3.1 的实时统计查询）。上量前建议开启并定好保留天数；开启后每日定时任务生效，不会立即清。

### 5.2 平台级观测

- **日志三类落点**：应用运行日志 → PG 主库表（`conversations`/`messages`/`workflow_*`）；trace 事件缓冲 → api storage 的 `ops_trace/` 目录（依赖 api↔worker 共享存储，见 §3.4）；进程日志 → 容器 stdout（pod 重建即失）。

- **Sentry**：`API_SENTRY_DSN` / `WEB_SENTRY_DSN` / `PLUGIN_SENTRY_*`（shared.env.example:66-70），默认空。
- **OTel**：见 §3.5，默认关。
- **CLS 日志/告警**：k8s README 已规划（pod 重建后 `kubectl logs` 失效的教训）；应用级 trace 可直接配 **tencent（CLS）provider**（§3.4），与腾讯系部署匹配。

### 5.3 其他注意点

- 统计接口按 `app_id` 实时扫表，大流量应用的概览页属于重查询；如需外部报表，建议自行查库或接 tracing 平台，不要直接高频调这些端点。
- 标注回复依赖 embedding 模型（插件）；换模型重建全部标注向量，大量标注时留意索引耗时。
- trace 凭证按 tenant 加密存储（`encrypt_token`），轮换 `SECRET_KEY` 类密钥时注意影响面。

## 6. 常见任务速查

| 任务 | 入口 |
|---|---|
| 看应用用量趋势 | 应用详情 → 概览；口径见 §3.1（调试不计入） |
| 排查单次对话/运行 | 日志页 → 详情抽屉（token/延迟/逐节点 trace） |
| 让某些问题固定回答 | 编排页开启标注回复 → 录入 Q&A → 调相似度阈值 |
| 深度性能分析 | 概览页「Tracing app performance」配 Langfuse/腾讯 CLS |
| 控制日志表膨胀 | 开 `WORKFLOW_LOG_CLEANUP_ENABLED` / `ENABLE_CLEAN_MESSAGES` + 保留天数（§5.1） |
| Dify 服务自身监控 | Sentry DSN / `ENABLE_OTEL` + OTLP / k8s 接 CLS |
