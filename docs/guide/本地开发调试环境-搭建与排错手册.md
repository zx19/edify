# 本地开发调试环境：搭建与排错手册

> 面向本仓库（edify / lomva 部署）的研发。
> 内容来源：本仓库代码 / 配置 / QA 集群实际部署，以及 2026-09-01 搭建过程中实测验证的结论。
> 关联文档：《工作空间机制说明-功能开发与运维手册》（认证链路）、《k8s/README.md》（QA 集群布局与密钥）。
> 标注约定：✅已实测证实 / ⚠️推导未实测 / ❌已证伪。

## 0. 调试模式选型（2026-09-08）✅

| 模式 | 数据面 | 执行引擎 | 适用 |
|---|---|---|---|
| **1. 连 QA**（§1-§8 主体） | QA PG 直连 + QA plugin-daemon / agent-backend（隧道） | 本地 web / dev-proxy / api | 只调 api、web 层；零额外配置 |
| **A. QA 数据 + 本地引擎**（§9） | QA PG 直连 + QA plugin-daemon（隧道） | 本地 web / dev-proxy / api / **agent-backend 源码** | 改 `dify-agent/` 代码——隧道跑的是 QA 镜像，本地 agent 改动不生效 |
| **全本地**（§10） | 本地空库 + 全本地容器 | 全本地源码 | 不碰 QA（无写污染）；从零造数据 |

判断标准：

- **要改 agent 代码吗？** 要 → 模式 A；不要 → 模式 1 够用
- **要 QA 存量数据吗**（复现线上问题、对着现有应用调试）？要 → 1 / A；造测试数据就够 → 全本地
- plugin-daemon 是否本地化只取决于**是否开发插件本体**（见 §9.4，非插件开发留隧道即可）

## 1. 架构与端口总览

本地开发的标准布局（三个进程 + 一条隧道）：

```
浏览器 localhost:3000 (next dev)
  ├─ 浏览器 XHR ──→ dev-proxy :5001 ──→ api :5002
  └─ SSR/RSC 服务端请求（/auth/refresh 等）──→ dev-proxy :5001 ──→ api :5002
                                          （走 CONSOLE_API_URL，见 §4）
api :5002（flask run --debug）
  ├─ PostgreSQL：QA TencentDB（直连公网域名）
  ├─ Redis：本地 :6379（空密码）
  ├─ plugin-daemon：QA 集群（kubectl port-forward :5010）
  ├─ agent-backend：QA 集群（kubectl port-forward :5050，agent 应用对话必需）
  └─ 对象存储：本地 api/storage/（fs，需拷私钥，见 §6）
```

| 端口 | 进程 | 说明 |
|---|---|---|
| 3000 | `next dev` | web 前端 |
| 5001 | dev-proxy | 唯一合法的 api 入口（浏览器与 SSR 都必须经它，见 §4） |
| 5002 | flask api | 本地 api；⚠️ 上游默认 5001，因 5001 被 proxy 占用而挪到 5002 |
| 6379 | redis（本地） | 队列/缓存/邀请 token 全在本地 |
| 5010 | kubectl port-forward | 隧道到 QA 集群 plugin-daemon:5002 |
| 5050 | kubectl port-forward | 隧道到 QA 集群 agent-backend:5050（agent 应用对话必需） |

## 2. 启动步骤

```bash
# 0) 依赖（首次）
./dev/setup                      # 复制 env 模板 + 装依赖

# 1) api（迁移自动执行）
uv run --project api flask run --host 0.0.0.0 --port=5002 --debug
#    等价 ./dev/start-api，但那个脚本用默认 5001，需自行确认参数

# 2) dev-proxy（必须先于/独立于 web 启动）
pnpm -C web run dev:proxy        # 读 web/.env.local 的 DEV_PROXY_TARGET

# 3) web
pnpm -C web run dev

# 4) QA plugin-daemon 隧道（长期开发放自己终端跑，别依赖会话）
kubectl -n qa-ai-lomva port-forward svc/plugin-daemon 5010:5002

# 5) QA agent-backend 隧道（调 agent 类应用必需，缺了对话一直 loading，见 §7-8；
#    模式 A 下此步省略，改为本地源码跑，见 §9）
kubectl -n qa-ai-lomva port-forward svc/agent-backend 5050:5050

# 6) 可选：celery worker（不发邮件/异步任务可跳过）
uv run --project api celery -A celery_entrypoint.celery worker --loglevel INFO -P solo
```

## 3. 本地连 QA 的数据面配置

本地调试的定位是「连 QA 数据调试」，与全本地中间件（`./dev/start-docker-compose`）是两种模式。连 QA 需要四个数据面：

### 3.1 PostgreSQL（直连）✅

`api/.env`（gitignored，从 `.env.example` 复制后改）：

```ini
DB_HOST=qa-postgres-default.xsl.link
DB_PORT=5432
DB_USERNAME=dev_svc_lomva
DB_PASSWORD=<从 k8s/overlays/qa/config/secret.env 取>
# 外部 PG 会掐空闲连接：死连接导致 flask-login 吞异常误判 401（登录后死循环）
SQLALCHEMY_POOL_PRE_PING=true
SECRET_KEY=<与 QA 一致，否则 DB 里已加密的模型凭据解不开>
```

⚠️ **写操作直接落在 QA 库上**——本地调试建的测试应用/知识库会出现在 QA 环境，注意清理；调试危险路径（删数据、迁移）前先想清楚。

### 3.2 Redis（本地）✅

`REDIS_HOST=localhost`、空密码。**故意不连 QA 的 redis**：redis 不只是缓存，还有 celery 队列与邀请 token。连 QA 的话，本地投递的异步任务会被 QA 的 worker 用 QA 的代码消费执行——本地改了代码实验时行为对不上，且可能污染 QA（限流锁、真实发邮件）。本地闭环邀请流程不受影响（token 存本地 redis，本地 api 自己读）。

### 3.3 plugin-daemon（port-forward 隧道）✅

`api/.env`：

```ini
PLUGIN_DAEMON_URL=http://127.0.0.1:5010     # 不是 5002！那是 api 自己
PLUGIN_DAEMON_KEY=<QA 轮换后的值，从 lomva-secret 取>
```

取 key：

```bash
kubectl -n qa-ai-lomva get secret -o name | grep lomva-secret | head -1 \
  | xargs kubectl -n qa-ai-lomva get -o jsonpath='{.data.PLUGIN_DAEMON_KEY}' | base64 -d
```

⚠️ 本地没跑 plugin-daemon；`PLUGIN_REMOTE_INSTALL_PORT`（5003）未转发，**本地装新 marketplace 插件会失败**，需要时再加一条 `port-forward svc/plugin-daemon 5011:5003` 并同步改 env。使用 QA 已装的供应商/模型不受影响。

### 3.4 agent-backend（port-forward 隧道）✅（2026-09-07 排障实测）

agent 应用的执行不在 api 进程里，api 把对话请求转发给独立的 agent-backend 服务
（QA 上 `lomva-agent-backend` Deployment，Service 端口恰为 5050）。本地没跑该服务，
必须隧道 + 同步 token：

```ini
AGENT_BACKEND_BASE_URL=http://localhost:5050   # 本地 .env 默认值，无需改
AGENT_BACKEND_API_TOKEN=<从 k8s/overlays/qa/config/secret.env 取 AGENT_BACKEND_API_TOKEN>
```

⚠️ token 上游默认是 dev 值，**QA 已轮换**，本地不同步会被拒（同 `PLUGIN_DAEMON_KEY` 的坑）。
缺隧道或 token 错的表现是**发消息一直 loading、无任何报错**：请求卡在 api→agent-backend
这一跳，plugin-daemon 无 dispatch 记录、messages 表不落新行（定位手段，见 §7-8）。
agent-backend 在集群内自行连 plugin-daemon/DB，本地调试的是 api 转发层，agent 执行逻辑
仍是 QA 部署版本（与 plugin-daemon 同理的取舍）。改了 env 需重启 flask（热载不监视 .env）。
要调试 agent 执行逻辑本身，改用模式 A——agent-backend 本地源码跑，见 §9。

### 3.5 对象存储（本地 + 拷私钥）✅

`STORAGE_TYPE=opendal` / `OPENDAL_FS_ROOT=storage`（默认即本地 fs）。租户 RSA 私钥存在存储卷（不在 DB），用于解密模型供应商凭据。本地不拷会报 `PrivkeyNotFoundError`（见 §7-4）：

```bash
mkdir -p api/storage/privkeys/<tenant_id>
kubectl -n qa-ai-lomva cp <api-pod>:/app/api/storage/privkeys/<tenant_id>/private.pem \
  api/storage/privkeys/<tenant_id>/private.pem
chmod 600 api/storage/privkeys/<tenant_id>/private.pem   # 该路径已被 gitignore
```

⚠️ QA 上传的历史文件（图标/附件）本地没有，浏览到时 404 属预期；本地新上传读写自洽。

### 3.6 邮件（不配）✅

`MAIL_TYPE=` 留空。前端会提示「邮件服务器未设置，无法发送邀请邮件」，属预期：发信是 celery 异步任务，本地没 worker 消费，配了也发不出。测邀请流程用邀请弹窗的**复制邀请链接**直接开本地地址，闭环且不打扰真实邮箱。

## 4. 请求路由：为什么所有入口都必须走 5001 ⚠️（已实测踩坑）

dev-proxy 对 cookie 做**改名隔离**（`web/node_modules/@langgenius/dev-proxy/src/cookies.ts`）：

- api → 浏览器方向：`access_token` 被改名为 `dev_proxy_<hash>_access_token`（并剥 Domain/Secure、Path 改 /，`localCookieScope: 'target-origin'` 按 target origin 哈希隔离，多套后端并存时互不串扰）
- 浏览器 → api 方向：proxy 翻译回普通名

因此 **`web/.env.local` 的 `CONSOLE_API_URL` 必须是 `http://localhost:5001`（proxy），不能是 5002（api 直连）**。SSR 服务端请求（`/auth/refresh` 路由、RSC 数据预取）经 `web/config/server.ts` 拼这个前缀发请求，并**原样转发浏览器 cookie**——直连 5002 就绕过了翻译，api 收到 `dev_proxy_xxx_refresh_token` 认不出，返回 401。

### 4.1 典型症状：登录成功却 401 死循环 ✅

```
POST /console/api/login          200   ← 登录成功，cookie 种了
GET  /console/api/account/profile 401   ← SSR 直连 api，cookie 名没翻译
POST /console/api/refresh-token   401   → 前端 303 回 /signin → 循环
```

判别方法：401 的那批请求（api 日志）不带登录用户语言、URL 带全路径的多为 SSR 代发。修法：`web/.env.local` 改 `CONSOLE_API_URL=http://localhost:5001` 后**重启 next dev**（env 不热载）。

### 4.2 api 侧 cookie 命名（QA 与本地不同）✅

`api/libs/token.py:72` `_real_cookie_name`：仅当 CONSOLE_WEB_URL 与 CONSOLE_API_URL 均为 https、无 COOKIE_DOMAIN、根路径部署时才用 `__Host-` 前缀。本地 http → 普通名 + `path=/`；QA（https 子路径）→ 普通名 + `path=/lomva`。QA 上 nginx 透传不改名，浏览器与服务端同名，故无本地这类问题。

### 4.3 dev-proxy 对 https 子路径上游的前缀错配（2026-09-29 实证并修复）✅

**症状**：本机代理目标指 qa-xai（https 子路径）时，登录 200 后 profile/refresh 全 401 弹回 signin——与 §4.1 同症状、**不同根因**。

**根因**：dev-proxy 回译 cookie 名用协议启发式（`server.ts` `useHostPrefix = targetUrl.protocol === 'https:'`）——目标只要是 https 就一律回 `__Host-` 前缀；而 qa-xai 因子路径部署发的是普通名（§4.2），读不到 `__Host-access_token` 即 401。该错配自 `8e6dd7219d`（api 子路径 cookie 化）引入后一直潜伏，直至首次走「console 登录 + 本机代理 + qa-xai」组合才暴露。

**修复（已入库）**：隔离名改为**无损保留上游真实 cookie 名**（`packages/dev-proxy/src/cookies.ts` `toScopedLocalCookieName` 不再抹前缀），回译原样奉还——qa-xai 回普通名、根路径上游（cloud.dify.ai）回 `__Host-`，与 §4 顶部「proxy 翻译回普通名」的描述在全部目标下成立。判断标准仍是 §4.1 的判别法；本根因无独立判别特征，配置正确（`CONSOLE_API_URL` 指代理）仍 401 循环即此问题。

## 5. `web/.env.local` 完整模板（连 QA 模式）✅

在 `.env.example` 基础上改这几项，其余保持默认：

```ini
NEXT_PUBLIC_BASE_PATH=                      # 根路径，QA 才是 /lomva

DEV_PROXY_PUBLIC_TARGET=http://localhost:5002
DEV_PROXY_HOST=127.0.0.1
DEV_PROXY_PORT=5001
```

## 6. 邀请/激活链路调试要点 ✅

本地复现「移除成员后重邀」这类流程时：

1. 邀请在本地发起 → token 存**本地** redis（`member_invite:token:<uuid>`，TTL 72h）
2. 登录/激活都打本地 api（读 QA 的账号表，join 表是本地写入 → 落 QA 库 ⚠️ 注意 §3.1 的写操作提示）
3. 排查顺序：api 日志（login/activate/refresh-token 的状态码序列）→ QA 库 `tenant_account_joins` → redis token 是否存在

## 7. 排错速查表

| # | 症状 | 根因 | 修法 |
|---|---|---|---|
| 1 | 登录 200 后 profile/refresh 全 401 循环 | `CONSOLE_API_URL` 指向 5002 直连，SSR cookie 名没翻译 | 改 5001，重启 next dev（§4） |
| 2 | `model-providers/summary` 404 `/plugin/...` | `PLUGIN_DAEMON_URL` 指向 api 自己（5002） | 改 5010 + 起 port-forward（§3.3） |
| 3 | 插件接口 401 | `PLUGIN_DAEMON_KEY` 是上游默认值，QA 已轮换 | 从 lomva-secret 取新值（§3.3） |
| 4 | `PrivkeyNotFoundError: Private key not found, tenant_id=...` | 租户 RSA 私钥在 QA 存储卷，本地 fs 没有 | `kubectl cp` 拷私钥（§3.5） |
| 5 | 「邮件服务器未设置」提示 | 本地 `MAIL_TYPE` 空 | 预期行为，不配（§3.6） |
| 6 | `workspace not found, please contact system admin...` | 账号无任何 tenant join（如被移除后） | 重邀走修复后的链路（`invite_new_member` 即时恢复 join，a7b59d9abb） |
| 7 | PG 间歇性 401 假象 | 外部 PG 掐空闲连接，池内死连接 | `SQLALCHEMY_POOL_PRE_PING=true`（默认应已开） |
| 8 | agent 对话一直 loading：无报错、plugin-daemon 无 dispatch 记录、messages 表不落新行 | 本地没转发 agent-backend（5050），或 `AGENT_BACKEND_API_TOKEN` 未同步 QA 轮换值 | 加 port-forward + 同步 token，改 env 后重启 flask（§3.4） |

## 9. 模式 A：agent-backend 本地源码（QA 数据 + 本地执行引擎）⚠️

> 2026-09-08 定稿未完整实测（启动命令与依赖安装已初步验证可拉起；token 链路未跑通验证）。

与模式 1 的**唯一区别**：agent-backend 从「QA 隧道（5050）」换成「本地源码」——`dify-agent/`
改动可 `--reload` 热载调试。PG / plugin-daemon（5010 隧道）/ 本地 redis / 私钥全部不变。

```
flask api(5002,本地) ─┬─ PG：QA 直连（不变）
                      ├─ redis：本地（不变）
                      ├─ plugin-daemon：QA 隧道 5010（不变）
                      └─ agent-backend：本地源码 :5050（替换原隧道）

agent-backend(5050) ├─ redis：本地 db2（key 带 dify-agent 前缀）
                    ├─ plugin-daemon：localhost:5010（隧道）
                    └─ inner API：localhost:5002（本地 api）
```

### 9.1 改动清单 ⚠️

**`api/.env` 一处**——`INNER_API_KEY_FOR_PLUGIN` 同步 QA 值（本地 agent-backend 回调本地
api 的鉴权 key；上游默认值 `QaHbTe...`，QA 已轮换。这是继 `PLUGIN_DAEMON_KEY`、
`AGENT_BACKEND_API_TOKEN` 之后第 3 个需要同步的 token，见 §9.3）：

```bash
sed -i '' "s|^INNER_API_KEY_FOR_PLUGIN=.*|$(grep '^INNER_API_KEY_FOR_PLUGIN=' \
  k8s/overlays/qa/config/secret.env | cut -d= -f2-)|" api/.env
```

**新建 `dify-agent/.env`**（`ServerSettings` 自动读取；值全部取自 `k8s/overlays/qa/config/secret.env`）：

```ini
DIFY_AGENT_REDIS_URL=redis://localhost:6379/2
DIFY_AGENT_PLUGIN_DAEMON_URL=http://localhost:5010
DIFY_AGENT_PLUGIN_DAEMON_API_KEY=<secret.env 的 PLUGIN_DAEMON_KEY>
DIFY_AGENT_INNER_API_URL=http://localhost:5002
DIFY_AGENT_INNER_API_KEY=<secret.env 的 DIFY_AGENT_INNER_API_KEY>
DIFY_AGENT_API_TOKEN=<secret.env 的 DIFY_AGENT_API_TOKEN，即 api/.env 的 AGENT_BACKEND_API_TOKEN>
```

**`dify-agent/.gitignore` 补一行 `.env`**——原文件只 ignore `dify-aio` 和 `site/`，密钥
文件有误提交风险（api/.env 靠仓库根 .gitignore 兜底，dify-agent 没有对应条目）。

### 9.2 启动与验证 ⚠️

```bash
# 1) 两条长跑进程（自己终端，勿依赖会话）
kubectl -n qa-ai-lomva port-forward svc/plugin-daemon 5010:5002
cd dify-agent && uv run --project . --extra server \
  uvicorn dify_agent.server.app:app --host 127.0.0.1 --port 5050 --reload

# 2) 重启 flask api（INNER_API_KEY_FOR_PLUGIN 改了，不热载）
# 3) 验证：浏览器发一条消息有回复即通
```

不通时的排查锚点：agent-backend 终端日志 → plugin-daemon 无 `127.0.0.1` dispatch 记录
（§7-8 的手段）→ agent-backend 回调 api 401 则查 §9.3 的三个 token。

### 9.3 本地必须与 QA 同步的 token 汇总 ✅

| token | 本地变量 | QA 来源 | 未同步症状 |
|---|---|---|---|
| plugin-daemon key | `PLUGIN_DAEMON_KEY` | lomva-secret | 插件接口 401（§7-3） |
| agent-backend token | `AGENT_BACKEND_API_TOKEN` | secret.env 同名 | agent 对话 loading（§7-8） |
| inner api key | `INNER_API_KEY_FOR_PLUGIN` | secret.env 同名 | agent-backend 回调 api 401 |

> QA 轮换任一 secret 后本地即失效——出现「昨天还好好的」类症状先核对这张表。

### 9.4 plugin-daemon 要不要也本地化？✅（结论）/ ⚠️（未实测路径）

**结论：非插件开发不要本地化**（留隧道零成本）。插件的「安装」= DB 记录（QA 共享库，
本地可读）**+ 本地存储卷的包文件**（QA pod PVC 实测 1.3G：`plugin/` 运行时 +
`plugin_packages/` 包缓存 + `assets/`）——本地新起 plugin-daemon 存储为空，DB 有记录、
文件缺失 → 插件不可用。要开发插件本体时二选一：

1. **拷卷**：`kubectl -n qa-ai-lomva cp <plugin-daemon-pod>:/app/storage docker/volumes/plugin_daemon/storage`
   （QA 镜像与 middleware compose 同为 `0.6.10-local` ✅，无缝兼容，含手动导入插件）
2. **重装**：marketplace 插件一键重装（DB 记录已在）；手动导入的 `.difypkg` 需重导

### 9.5 模式 A 的边界 ⚠️

- agent 工具执行（shellctl / `local_sandbox`）未配置——纯对话、知识库检索不受影响；
  要调工具执行再加 `local_sandbox` 隧道或本地容器（full compose 有定义）
- Agent Stub 相关（`DIFY_AGENT_STUB_API_BASE_URL` / `SERVER_SECRET_KEY`）未配置，遇到
  stub 场景再补（secret.env 有 `DIFY_AGENT_SERVER_SECRET_KEY`）
- agent 运行时状态在本地 redis db2，与 QA 互不干扰；落库记录仍写 QA 库（模式 A 固有属性）

## 10. 全本地模式（概要）⚠️

`docker/docker-compose.middleware.yaml`（`./dev/start-docker-compose`）自带全套中间件：
`db_postgres(5432)`、`redis(6379, 密码 difyai123456)`、`sandbox(8194)`、`plugin_daemon`、
`ssrf_proxy(3128)`、`weaviate(8080)`；`api/.env.example` 默认值即按此设计。agent_backend
不在其中，需从 full compose 抄服务或按 §9 源码跑。

要点与坑：

- **5002 端口撞车**：plugin_daemon 默认映射宿主 5002 = 本地 api 端口。
  `docker/middleware.env` 设 `EXPOSE_PLUGIN_DAEMON_PORT=5010`，`PLUGIN_DAEMON_URL` 保持 5010
- **plugin-daemon 回调**：compose 内无 api 服务，`middleware.env` 设
  `PLUGIN_DIFY_INNER_API_URL=http://host.docker.internal:5002`（服务已配 extra_hosts）
- **redis 带密码**：本地 redis 换为 compose 实例后，`REDIS_PASSWORD=difyai123456`
- **凭据不可迁移**：QA 库里模型供应商凭据是 QA 私钥加密的，本地解不开——全本地需重新
  配 API key；空库走一遍 setup 向导 + marketplace 装插件（本地 plugin-daemon 的 5003 直连，
  无 §3.3 的安装限制）
- **双模式切换**：建议 `api/.env.qa-hybrid` / `api/.env.full-local` 两份存档，切换 = cp 覆盖
  + 重启 flask
- 收益：写操作不再落 QA 库（§3.1 的风险敞口关闭）；代价：无 QA 存量数据，从零造数据
