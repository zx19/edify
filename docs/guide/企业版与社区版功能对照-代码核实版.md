## 结论（对本仓库决策的实际意义）

对企业版真正有依赖的**只有三行**，且都已有替代路径：

| 企业版能力 | 替代路径 |
|---|---|
| SSO | 网关层 SSO 前置；或自研（`AccountIntegrate` 表可作接入点） |
| WebApp 访问控制 | 自研 internal（WebApp 手册 §2.2 改造点，中等工作量）或网关鉴权 |
| RBAC 细粒度 | 《权限体系自研总体方案》流 A（本地实现 `_inner_call` 层） |

其余行要么是商务/资质项（SOC 2、SLA、授权），要么社区版已具备或表述有误（日志保留、Tracing、多工作空间、角色体系）。

> 商业授权提示：Dify 社区版是 Apache 2.0 修改版（附加条款：不得移除控制台 Logo/版权信息、多租户 SaaS 需授权等），二开分发前建议读一遍仓库 LICENSE。

## 附：企业版实现架构（从开源接缝反推）

官方未公开企业版架构文档；以下从本仓库 `api/services/enterprise/` 等接缝反推，置信度除标注外为高。

**形态：闭源功能是一组独立服务，社区版 api 以 HTTP 客户端接入**（`EnterpriseRequest`：Secret-Key 头 + tenant/account 头 + traceparent 透传；超时通用 5s / RBAC 30s）：

| 服务 | 接入配置 | 承担能力 |
|---|---|---|
| dify-enterprise 主后端 | `ENTERPRISE_API_URL` | license/特性下发（`feature_service.py:23/393`）、SSO 发起、WebApp 访问模式存取、空间权限、MCP token |
| RBAC 子服务（可独立部署） | `ENTERPRISE_RBAC_API_URL`（`/inner/api/rbac/*`） | check-access、角色、策略、访问矩阵全量 |
| 企业插件管理器 | `ENTERPRISE_PLUGIN_MANAGER_API_URL` | 插件管控 |
| telemetry collector | OTLP（`ext_enterprise_telemetry`） | 企业观测数据 |

其他反推：SSO 登录流程由企业后端承担，本地仅存 `AccountIntegrate` 绑定关系；审计日志本仓库无采集/存储，大概率也在企业后端（中置信）；本地库为主，`account_deletion_sync.py` / `workspace_sync.py` 向企业后端同步状态；前端同一套 web 按 `systemFeatures` 切换 UI（企业版是否另有独立管理控制台无法确认，推测有）。

**对自研的启示**：官方架构本身就是"判定外置 + 统一出口"——我们把外置服务换成本地实现（`_inner_call` 替换点与企业服务边界一致）；他们连每请求 HTTP 外呼 + 30s 超时都接受了，本地 PG + 缓存只会更快。
