## 2. 角色模型 ✅（层级表述需修正）

枚举（`api/models/account.py:21`）：`owner / admin / editor / normal / dataset_operator`。
能力边界（以 `check_member_permission` 与装饰器硬校验为准）：

| 角色 | 边界 |
|---|---|
| owner | 全控、唯一、不可移除、可转让（需邮件验证码） |
| admin | 成员/模型/集成管理 + editor 能力（不能动 owner） |
| editor | 建改应用/工作流/知识库 |
| normal | 仅用已发布应用 |
| dataset_operator | 仅知识库操作 |

⚠️ **修正**：代码中**没有角色层级/继承机制**，只有并列枚举 + 手工集合的闸门方法（`is_privileged_role`=owner/admin、`is_editing_role`=+editor、`is_dataset_edit_role`=+dataset_operator）。"层级包含"是理解模型，不是代码结构。

## 3. RBAC 现状 ✅ / ABAC ❌

**三个核心概念的分工**：

- **角色（Role）**：空间级身份能力，"你是谁"（workspace 域权限点，如成员管理、插件安装）——整个空间一刀切。
- **访问策略（AccessPolicy）**：资源级权限的容器，"对某个具体 app/dataset 能做什么"（资源域权限点，如 `app.acl.edit`）。结构 = 一组资源域键 × 绑定（角色|成员）× 层级（workspace 默认 | 具体资源覆盖）。前端对应「权限集 / Access Rules」tab。解决"能编辑应用 A 但只能看应用 B"这类角色做不到的精细授权。
- **权限快照（`GET /rbac/my-permissions`）**：把当前用户全部权限一次算好打包下发（workspace 键 + app/dataset 的"默认键 + 资源 overrides"），供前端本地判断 UI 显隐与列表打标——避免每个按钮一次 check-access 外呼。是"请求时刻的视图"，服务端判定永远以当时为准。

**两套键拼写（实现要点）**：点分格式 `app.acl.preview` 用于存储/快照/前端 `hasPermission`（角色与策略的 permission_keys）；下划线格式 `app_view_layout` 是判定 scene（`RBACPermission` 枚举值，装饰器发给 check-access）。同一语义两套拼写，判定层负责 scene→键映射（总体方案 §5）。

**资源可见性（如"某 app 仅自己可见"）的生效链**：限制存白名单（scope=only_me/specific + account_ids）；生效为双闸门——① 列表页：`resolve_app_access_filter`（`controllers/common/app_access.py:68`）综合 my-permissions 快照与 `whitelist_resources` 生成过滤条件注入列表 SQL；② 直接访问 URL：接口装饰器走 check-access（无 `app.acl.preview` → 403）。可见性（白名单）与能力（策略键）是两个独立维度。

- RBAC：企业版判定在闭源后端，本地经 `_inner_call` 转发；权限点约 50 个（`core/rbac/entities.py`），作用域 workspace/app/dataset 三级 + 白名单 ALL/SPECIFIC/ONLY_ME。自研本地化见《权限体系自研总体方案》流 A。
  - 两个易混枚举（`core/rbac/entities.py:4/16`）：`RBACResourceScope` 是**判定维度**（这次检查挂在哪级资源：workspace 级无资源 id，app/dataset 级需 resource_id，驱动装饰器提取 id 与 maintainer 短路）；`RBACResourceWhitelistScope` 是**配置维度**（资源对谁可见：all/specific/only_me，用于访问配置 API）。
  - 企业版实现可从 DTO 反推（高置信）：内置角色/策略（is_builtin）、创建者自动绑定（sync_creator_access_policy_member_bindings + is_locked 系统绑定）、权限快照=默认键+资源级 overrides、角色可复制成员；推不出的是 check-access 内部精确语义与存储结构（合同测试校准）。
- ❌ **ABAC（部门/标签/时间/IP 因子、PDP 引擎、声明式策略、导入导出）**：本仓库零实现，企业版公开资料亦无此能力——属**超出企业版的设计目标**。如要做，见 §6 的最小落地路径。
- ✅ **凭据维度管控有企业版实证**：`ENTERPRISE_DISABLE_RUNTIME_CREDENTIAL_CHECK`（configs/enterprise，"关闭时仅保存 workflow 时检查"）+ `workflow_service.py` / `core/model_manager.py` / `core/tools/tool_manager.py` 的 credential policy 引用。

## 4. 组织级层 ❌（这是我们的扩展设计，非现状）

- 权限枚举只有 workspace/app/dataset 三级，**无 organization scope**；"组织管理员与各空间角色取并集"是《权限体系自研总体方案》流 B 的目标模型。
- 落地方式已设计：角色绑定表加 `scope`（organization 时 tenant_id 为空），判定时两级并集。

## 6. 执行流程（修正版）

⚠️ 原文描述的"统一 PDP 入口"不存在。实际流程：

```
请求 → Flask-Login request_loader 解析 JWT（ext_login.py:56）
     → load_user 恢复 current_tenant/role（account_service.py:321）
     → 各接口装饰器分散判定：
         RBAC_ENABLED=false → 传统角色硬校验（check_member_permission / is_*_role）
         RBAC_ENABLED=true  → rbac_permission_required → check-access
                              （maintainer 短路放行，common/wraps.py:110）
     → 拒绝抛 403
```

## 7. 若要做 ABAC：最小落地路径（愿景的工程化）

一期只做**资源标签**一个因子（部门/时间/IP 不做）：

1. `apps`/`datasets` 加 `sensitivity_tag` 字段（或复用现有 tag 体系）；
2. 角色/策略增加 `deny_tags` 约束列；
3. 判定收口点（总体方案 §5 check-access + 列表过滤）加 tag 断言；
4. 声明式策略/PDP/导入导出**不做**——硬编码断言即可覆盖"监管等级"类需求。
