# 基于 Dify 二开：web + webapp 重写方案（去 Dify 化 + 合规）

> **战略前提（逐轮确认）**：
> ① 差异化产品 + 断流自研（fork 后不 merge 上游）
> ② V1 全部功能保留、不做差异化、只删减
> ③ **V1 核心目标：去 Dify 化 + 合规** ← 这是必须重写的真正理由
>
> 技术栈保持 React + Next.js，`@xsl/lomva-ui` 同依赖重构，底层 `@base-ui/react` 复用。
>
> **License 事实（2026-09-09 核实仓库根 LICENSE）**：Dify 为 **modified Apache 2.0 + 附加条款**
> （非 AGPL，无开源传染义务），但有 1a 多租户限制 + 1b 前端 LOGO 锁定 + 外观专利三条硬约束，
> 详见 §2.2。**在 Dify 前端上直接换 logo 违反 1b；重写前端是合法解除品牌锁定的路径。**

---

## 0. 为什么"去 Dify 化"是重写的硬理由（而非删减能解决）

删减只能删功能，**去 Dify 化要抹掉身份痕迹**。Dify 的痕迹散落在 web 约 4500 个文件的
代码、文案、包名、配置里，不是删几个模块能消除的。重写是去 Dify 化的最佳载体。

---

## 1. 去 Dify 化：三大痕迹面（V1 核心工程目标）

### 1.1 品牌痕迹（用户可见）

| 痕迹                                   | 位置                                                                                                        | 现状   |
| -------------------------------------- | ----------------------------------------------------------------------------------------------------------- | ------ |
| 产品名 / logo / favicon / title / meta | `web/public/`、`app/layout.tsx`、路由元数据                                                                 | 待替换 |
| 用户可见文案中的 "Dify"                | `i18n/`：**24 个语言目录**，每语言 18 个文件、约 78 处 Dify 字样（zh-Hans 实测），全语言合计约 **1900+ 条** | 待替换 |
| 登录/导航/footer/邮件模板文案          | 各组件                                                                                                      | 待替换 |

### 1.2 代码命名空间（工程痕迹，最重）

| 包             | 现状                                                             | 目标                                                                                   |
| -------------- | ---------------------------------------------------------------- | -------------------------------------------------------------------------------------- |
| `web`          | `dify-web`                                                       | 杏树林命名                                                                             |
| 组件库         | `@xsl/lomva-ui`                                                  | 新命名空间（**web 约 3280 个源文件中 1720 个 import 它（实测 52%），替换牵动面最大**） |
| dev 工具       | `@langgenius/dev-proxy`                                          | 新命名空间                                                                             |
| 契约/图标/配置 | `@dify/contracts`、`@dify/iconify-collections`、`@dify/tsconfig` | 新命名空间                                                                             |

### 1.3 基础设施痕迹

| 痕迹                                  | 位置                                              |
| ------------------------------------- | ------------------------------------------------- |
| Docker 镜像名 / tag                   | `web/Dockerfile`、`docker/`                       |
| 环境变量前缀                          | `env.ts`、`.env.example`（DIFY__/ NEXT_PUBLIC__） |
| cookie / localStorage key、埋点事件名 | `service/`、`utils/`、analytics                   |
| README / AGENTS / CLAUDE 文档         | 全仓库                                            |

### 1.4 去 Dify 化执行策略

1. **⚠️ 品牌层先行有前提**（原计划"1~2 周在现有前端换 logo 快速见效"**违反 LICENSE 1b**，
   在 Dify 前端代码上移除/修改 LOGO 是违约动作）。合法执行条件二选一：
   - 已购买商业许可（含白标授权）→ 可立即在现有前端执行；
   - 未购买 → 品牌替换**只能在新写代码中落地**（branding 集中配置入口先行搭好，
     logo/名称/文案/包名走单一配置，但不在 Dify 前端生效，随重写切换）。
2. **代码层随重写完成**：重写新代码直接用新命名空间，`@xsl/lomva-ui` → 新包名通过
   tsconfig path alias + 批量重命名（AST 工具）+ 全量编译/测试验证。
3. **基础设施层收口**：Docker 镜像、env 前缀、cookie/key、埋点随部署统一替换。

## 2. 合规：两条线（工程线 + 法务线，必须分开）

### 2.1 工程合规（团队可做）

| 项                  | 工具/动作                                                           |
| ------------------- | ------------------------------------------------------------------- |
| 供应链 license 扫描 | FOSSA / ScanCode / `license-checker`，清点依赖 license 类型         |
| 依赖漏洞            | `pnpm audit` / `npm audit`，高危必须修                              |
| 第三方 SDK 数据出境 | Amplitude（分析）、Sentry（错误上报）——医疗数据脱敏、关闭或境内部署 |
| 安全审计            | 密钥扫描、越权、XSS、注入（`lint:a11y` + 安全扫描）                 |

### 2.2 法务合规（⚠️ 必须律师介入，工程无法自行判定）

> **License 事实（以仓库根 LICENSE 文件为准，2026-09-09 核实）**：
> Dify 采用 **modified Apache 2.0 + 附加条款**（**不是 AGPL**，无开源传染义务），附加两条关键限制：
>
> - **1a 多租户限制**：未经书面授权，不得用 Dify 源码运营多租户环境
>   （1 workspace = 1 tenant）。杏树林是医疗 SaaS：若一套部署服务多家医院/机构
>   （每家一个 workspace）= 多租户，需商业授权；若每客户独立部署单 workspace
>   则不构成。**部署形态决定是否需要购买授权，必须先定。**
> - **1b LOGO/版权锁定**：使用 Dify 前端（`web/` 目录或 web 镜像）时，
>   **不得移除或修改控制台及应用中的 LOGO 与版权信息**。
>   条款明文"该限制不适用于不涉及 Dify 前端的用途"——
>   **重写前端恰是合法解除此锁定的路径**（前提是重写不构成对前端代码的复制）。
> - **外观专利**：LICENSE 末尾声明"本产品的交互设计受外观专利保护"。
>   V1 要求"原样保留 + 视觉回归确保一致"，**高保真复刻交互设计去替换原产品，
>   可能落入外观专利范围**——与 V1 策略存在直接张力，需法务评估相似度边界。
>
> **对原方案的重要修正**：此前版本误按 AGPL 分析，得出"重写无法解除开源义务"的
> 结论。事实相反：Apache 2.0 下 SaaS 衍生代码**无开源义务**，重写前端反而能
> 合法解除 1b 的品牌锁定。**重写这个结论幸存，但理由彻底改变。**
>
> 合规路径（需法务评估后选择）：
>
> - **重写前端 + 单租户部署**（每客户独立部署）：零授权成本，1b 自动解除；
> - **购买 Dify 商业许可**：若必须多租户 SaaS 形态，或想让"现有前端直接换 logo"
>   合法化（企业版通常含白标授权）——最快但花钱；
> - **仅内部使用**（杏树林自用、单 workspace）：Apache 2.0 基础上仅受 1b 约束，
>   保留 Dify 品牌即可用，重写后连 1b 也解除。

**结论**：前端重写能解决"品牌/代码去 Dify 化"和"工程合规"，并且是**解除 1b logo
锁定的合法路径**；但**多租户授权（1a）与外观专利风险**必须与法务并行确认，
不能指望代码层完成。

## 3. 功能层：V1 全部保留 + 只删减

- **保留**：Dify 现有全部功能，原样保留（控制台 `(commonLayout)` + webapp `(shareLayout)`）。
- **删减**：唯一允许的改动是删除不需要的模块（如 education、部分 marketplace 集成、多余语言包）。
- **不做**：品牌差异化、新功能、交互范式改造（全部推迟到 V2）。

能力盘点退化为**两分类**：保留 / 删除（无改造、无新增）。

## 5. 重写策略

### 5.1 顺序

1. **法务确认（并行启动，不阻塞工程）**：多租户部署形态（1a）+ 外观专利相似度边界 + 是否购买商业许可
2. **branding 集中配置**（搭好单一入口，logo/文案/包名集中化；未购许可则不在 Dify 前端生效）
3. **能力盘点**（保留/删除两分类）+ **基线固化**
4. **dify-ui 契约冻结 + 逐原语重构**（public API 冻结，随重写换新命名空间）
5. **底座地基**：service 契约、i18n、主题、布局、认证（含 webapp-signin）
6. **底座主旅程**：控制台 apps/workflow + webapp chat/agent
7. **底座次级模块**：知识库/工具/账户/skills
8. **删减执行**：删除不需要的模块
9. **基础设施去 Dify 化收口**：Docker/env/cookie/埋点
10. **一次性切换 + 回滚 + 监控**

### 5.2 关键原则

- **命名空间替换贯穿全程**：新代码从第一天就用新包名，不出现 `@langgenius` / `@dify` / `dify-web`。
- **品牌集中配置**：所有品牌元素走单一 branding 入口，未来换品牌零改动。
- **法务并行**：多租户（1a）与外观专利评估与前端重写同时推进，不等前端重写结果。
- **不在 Dify 前端上改 logo**（除非已购商业许可）：这条是 LICENSE 1b 的硬约束。

## 6. 测试体系（六层）

单元（Vitest/happy-dom）→ 浏览器组件（Vitest/Chromium）→ 组件库（Storybook）→ E2E（Playwright+Cucumber 37 feature）→ 视觉回归 → 契约（service + dify-ui 冻结 API）。

四原则不变：断言行为、真实边界 mock、语义选择器优先、coverage 是信号不是目标。
